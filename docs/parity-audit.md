# Feature parity: solar-array-simulator and this Exact port

Audit of `main` as it stands. No feature code was changed. Exact's pin (`.exact-ref`) was left alone.

| | |
|---|---|
| React Native source | [benjaminkomen/solar-array-simulator](https://github.com/benjaminkomen/solar-array-simulator) @ `9635d0526451d53dddce49a53386d69186d2b078` |
| Exact port | this repo @ `be4262220bbaa512eef5f7348d01df60665bbd15` |
| Exact checkout used to build | [expo/exact](https://github.com/expo/exact) @ `2b161aa120892cb8627baea45065e1b9804ddfc2` (the pin in `.exact-ref`) |
| OpenSpec | `openspec/specs/panel-placement/spec.md` is the only spec. It records the layout editor's current rules. |

Status words:

- **Matches** — the same user-visible behaviour.
- **Partial** — the screen or control exists, and a concrete piece is absent or weaker.
- **Implemented differently** — both sides do the thing, and the results differ.
- **Implemented wrongly** — the port has the control, and the result is broken relative to the RN app.
- **Missing** — the user cannot do it here.

Size, for the missing or partial work: **S** a local change, **M** a screen or a package wired through, **L** a new pipeline.

## What was run

**Exact, this machine.** `bun exact.mjs test web` during toolchain setup: 6 passed, 0 failed (wizard skip, mock grid with drag/rotate/zoom/link, compass to 90° then 180°, production menu, 200 ms zoom easing, simulation hour/season/engine). Then `bun exact.mjs web-build --out dist`, served with `bun exact.mjs serve dist`, and driven in headless Chrome at 390×844, light and dark. Screenshots are in `docs/parity/`. Findings marked **run** come from that session. Findings marked **code** were read and not exercised in the browser.

**React Native, this machine.** `bunx expo start --web` installed and Metro started, then the bundle failed:

`Unable to resolve "./wa-sqlite/wa-sqlite.wasm"` from `expo-sqlite/web/worker.ts`, pulled in by `src/utils/storage.ts`.

So there are no RN pixels from this run. Two further limits would remain even if that import resolved: `src/app/config.web.tsx` renders "Configuration is not yet implemented for this platform.", and `src/components/screens/CustomScreen.tsx` does the same for the layout editor. Welcome, photo, analyze, production, and simulation are the screens that exist on RN web. The repo's own iOS shots live under `solar-array-simulator/docs/screenshots/ios/` and were not recaptured here.

The port's README still says Production has no Simulate button, and that a direct open of the simulation URL starts at Welcome. This build has the button, and reloading the simulation URL stays on Simulation with empty in-memory state (0 W).

## Placement spec, checked against `app.ts`

The OpenSpec scenarios that the port's functions implement the same way as `src/utils/neighborSnap.ts`, `gridSnap.ts`, `collision.ts`, and `panelUtils.ts`:

- Landscape is 120×60.
- An 8 px gap is clear and a 7 px gap collides. A panel does not collide with itself (`collidesWithAny` skips `excludeId`).
- Neighbour candidates are the shared edge, then the positive side, then the negative side, in stored order. The first equal distance wins because the comparison is strict `<`.
- Release at (100, 10) against a panel at (0, 0) resolves to (68, 0). Release at (34, 200) keeps the shared edge. Release at (159, 400) is outside 90 px and becomes (150, 390).
- A drop onto another panel returns to the drag start.
- Add on an empty 400×800 canvas lands at (180, 330): `snapToGrid((400 − 60) / 2)` and `snapToGrid((800 − 120) / 2)`.

Two spec scenarios the port does not meet are in the table: the new panel is not selected, and bring-to-front happens on drop rather than at gesture start. Both match the RN utilities for the maths. Selection and z-order are the editor around those utilities (`usePanelsManager.ts`, `SolarPanelCanvas.tsx`).
